# FailProducts — Architecture Decision Records

## ADR-001 — Use Next.js

**Status:** Accepted

### Decision

Use Next.js App Router with TypeScript.

### Reason

The product needs both SEO-heavy public pages and interactive authenticated dashboards. Next.js provides a strong model for server-rendered public content alongside interactive application areas.

## ADR-002 — Deploy Next.js to Cloudflare Workers

**Status:** Accepted

### Decision

Use Cloudflare Workers instead of Vercel for the initial hosted deployment.

### Reason

The project is intended to keep infrastructure cost extremely low and already targets the Cloudflare ecosystem for CDN, R2, Turnstile, and future jobs.

Cloudflare currently recommends vinext for new Next.js applications on Workers. Because vinext is beta, compatibility testing is mandatory before production upgrades.

## ADR-003 — Use Neon PostgreSQL

**Status:** Accepted

### Decision

Use Neon PostgreSQL with Drizzle ORM.

### Reason

PostgreSQL provides a strong foundation for relational directory data, moderation, status history, comments, waitlists, and future analytics. Neon’s serverless/scale-to-zero model is appropriate for a low-traffic MVP.

## ADR-004 — Use R2 for media

**Status:** Accepted

### Decision

Use Cloudflare R2 instead of database blobs or a separate image vendor.

### Reason

R2 has a useful free allowance and free egress, and it keeps the storage system close to the application runtime.

## ADR-005 — Use ZeptoMail

**Status:** Accepted

### Decision

Use ZeptoMail for transactional email.

### Reason

The user explicitly selected ZeptoMail, and it fits the low-volume transactional use case.

## ADR-006 — Use shadcn/ui

**Status:** Accepted

### Decision

Use shadcn/ui as the baseline component library.

### Reason

It provides accessible, customizable components without requiring a separate runtime component framework and reduces design/build time for a solo maintainer.

## ADR-007 — No monorepo in MVP

**Status:** Accepted

### Decision

Keep one application repository.

### Reason

A monorepo would add package/workspace overhead before there are multiple independently deployed applications/packages.

## ADR-008 — No Redis/RabbitMQ in MVP

**Status:** Accepted

### Decision

Do not introduce Redis or RabbitMQ initially.

### Reason

The MVP does not have a workload that justifies the operational burden. Add Cloudflare Queues or another background system only when real asynchronous workloads appear.

## ADR-009 — External payment links instead of marketplace payments

**Status:** Accepted

### Decision

Creators may add external payment links, but FailProducts does not process/split payments in MVP.

### Reason

This lets creators receive money directly and avoids KYC, payouts, disputes, marketplace compliance, and payment infrastructure.

## ADR-010 — Referral tracking before full analytics verification

**Status:** Accepted

### Decision

Track outbound clicks generated by FailProducts before integrating third-party analytics.

### Reason

Outbound referrals are directly observable and cheap to calculate. Total external traffic is not observable without a creator-owned analytics integration.

## ADR-011 — No public failure score in MVP

**Status:** Accepted

### Decision

Do not create a single “failure score.”

### Reason

A numerical score would create unnecessary gaming, controversy, and moderation burden. Present individual signals and community opinions instead.

## ADR-012 — Product listings are owner-only in MVP

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Only a product's owner or founder may publish a listing about it. Third-party listings —
where a stranger lists someone else's product as failed — are out of MVP scope.

### Reason

FailProducts publishes statements about real businesses, attached to named people, under
headings like "failed" and "abandoned". Where the founder submits the listing, that is
self-disclosure: there is consent, a lawful basis for processing personal data, and a subject
who can withdraw. Where a third party submits it, the platform is publishing a potentially
defamatory factual claim about an unwilling subject, and it owes that subject a notice,
objection, and takedown process that does not exist and cannot be operated part-time.

The project is maintained by one person with a full-time job and no legal budget. This
constraint removes the majority of the legal exposure for a cost the product can absorb.

### Rejected alternatives

- **Open third-party submissions** — requires pre-publication human moderation, a delist route
  for non-users, an evidence standard, a takedown SLA, and reviewed Terms. Each is real
  ongoing work, and the failure mode is a legal claim against an individual.
- **Community nominations held for owner claim** — a reasonable middle path and the most
  likely Post-MVP direction, but it still creates a queue that must be worked, and a nominated
  product sitting unpublished has ambiguous status.

### Consequences

The directory grows more slowly and cannot list well-known failures whose founders have not
opted in. Cold-start becomes an outreach problem rather than a scraping problem, and the
roadmap must budget for that. In exchange, moderation load at launch is near zero and the
moderation surface can stay simple.

Reversal cost is moderate: opening submissions later is additive, but requires the full system
listed in `docs/LEGAL.md` §2 first.

## ADR-013 — Publication state, moderation state, and failure status are separate columns

**Status:** Accepted
**Date:** 2026-08-31

### Decision

A product carries three orthogonal fields, never collapsed into one enum:

```text
publication_state   DRAFT | PENDING_REVIEW | PUBLISHED | ARCHIVED
moderation_state    NONE | FLAGGED | HIDDEN | REMOVED
failure_status      STRUGGLING | LOW_TRACTION | ABANDONED | SHUT_DOWN | RECOVERING
```

### Reason

The MVP requirements described these as one pipeline, mixing `REMOVED` — a moderator action —
into the same enum as `STRUGGLING`, which describes the product itself, while separately
defining a moderation state list. They are independent dimensions. A product can be published
and flagged, or hidden while recovering, or archived by its owner while never having been
moderated.

Collapsing them produces impossible states, forces a moderator action to destroy the product's
factual status, and makes ordinary queries — "all flagged products that are still published" —
inexpressible.

### Rejected alternatives

- **Single status enum** — simplest to write, and the reason the ambiguity arose. It cannot
  represent the combinations the moderation and recovery features both require.
- **Status plus a boolean flag set** — booleans multiply and lose ordering; `is_hidden` and
  `is_removed` both true is another impossible state.

### Consequences

Three columns and three small state machines instead of one. Every list query filters on
`publication_state` and `moderation_state`; forgetting one leaks hidden content, so the
repository layer must make the safe default the easy one. `product_status_history` records
transitions on all three axes with the actor and reason.

## ADR-014 — Passwordless authentication

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Authentication is email OTP / magic link plus GitHub OAuth. No passwords are stored, and there
is no password reset flow.

### Reason

Two forces point the same way. First, security: no password store means no credential
stuffing, no reset-token flow, no breach-password checks, and no hashing parameters to get
wrong. Second, the runtime: Cloudflare Workers has no native argon2 or bcrypt, so a
password-based design would need a Web Crypto KDF, and a KDF tuned strongly enough to be worth
having would consume a meaningful share of the CPU budget on every login.

The product already depends on ZeptoMail for transactional email, so the delivery channel
exists. The audience is technical, so GitHub OAuth covers a large share of users directly.

### Rejected alternatives

- **Email and password** — familiar, but adds a password store, a reset flow, and expensive
  KDF work on a metered CPU budget, for no capability this product needs.
- **GitHub OAuth only** — cheapest and simplest, but excludes non-GitHub founders, and the
  product's subject matter is not limited to developers.

### Consequences

Email deliverability becomes a hard dependency of login, not just of notifications. SPF, DKIM,
and DMARC must be correct before launch, and a ZeptoMail outage becomes a login outage —
GitHub OAuth is the mitigation. Token handling becomes the critical security surface: single
use, short lived, hashed at rest, constant-time compared, attempt-capped, and consumed
atomically.

## ADR-015 — AGPL-3.0-only with DCO sign-off and a trademark carve-out

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Application code is licensed AGPL-3.0-only. Documentation is CC BY 4.0. Contributions require
Developer Certificate of Origin sign-off (`git commit -s`). The FailProducts name and logo are
excluded from the code licence via `TRADEMARK.md`.

### Reason

AGPL was already the stated intent, and it fits: the value of this project is the hosted
directory, and AGPL requires a hosted fork to publish its modifications.

DCO adds provenance at almost no friction — one flag on the commit — where a CLA would add
paperwork and deter drive-by contributions to a young project.

The trademark carve-out matters specifically because AGPL invites forks. Without it, a fork
can run the software *and* present itself as FailProducts, and users cannot tell the official
instance from a copy.

### Rejected alternatives

- **AGPL with a CLA** — preserves the option to relicense or dual-license later, but adds a
  signing step that suppresses small contributions.
- **AGPL with no DCO** — the original plan. Lowest friction, but no provenance record at all.
- **MIT or Apache-2.0** — permits a closed hosted competitor, which is the outcome the licence
  choice exists to prevent.

### Consequences

Without a CLA, the project cannot be relicensed or dual-licensed later without every
contributor's agreement. This is accepted knowingly and recorded in `docs/LEGAL.md` §8. AGPL
may deter some corporate contributors. Every commit must carry a sign-off line, which the
contribution documentation must make obvious.

## ADR-016 — Cloudflare Workers Paid plan is the deployment baseline

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Production runs on the Workers Paid plan from launch. The Free plan is for local experiments
only.

### Reason

The Workers Free plan caps CPU at **10 ms per request** (verified against Cloudflare's limits
documentation, 2026-08-31). Server-rendering a React Server Component page with database reads
will exceed that regularly, and the failure mode is a request terminated mid-render rather
than a slow page. Free also caps subrequests at 50 per request.

Paid raises the CPU limit to 30 seconds by default and removes the daily request cap, for $5
per month. Designing around a 10 ms budget would distort every rendering decision in the
project to save an amount of money that is not material.

### Rejected alternatives

- **Free plan with aggressive static generation** — pushes rendering to build time, but the
  directory has authenticated dashboards and user-generated comments that cannot be fully
  static, and it would still leave every dynamic path on a 10 ms edge.

### Consequences

A hard floor of roughly $5/month. Cost guardrails in `docs/DEPLOYMENT.md` §11 become more
important, not less, because Paid bills on usage — a runaway loop now costs money instead of
returning an error. A CPU limit must be configured explicitly to cap the downside.

## ADR-017 — Layered rate limiting

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Rate limiting uses three layers, chosen by what the limit is protecting:

| Layer | Use for |
|---|---|
| Cloudflare WAF rate-limiting rules | coarse flood protection at the edge, before Workers bill |
| Workers `ratelimit` binding | cost control and casual abuse on ordinary endpoints |
| Database or Durable Object counters | login, OTP verification, and anything needing an accurate global count |

### Reason

The security requirements mandate limits on nine endpoint classes but named no mechanism, and
on Workers the naive approach does not work — module-level counters live in isolates that are
shared and recycled, so an in-memory limiter is both wrong and a cross-request leak.

The layers differ in a way that matters. The Workers `ratelimit` binding (GA since September
2025) is documented as permissive, eventually consistent, and per-colocation. That is fine for
keeping a scraper from burning the request budget. It is **not** sufficient for brute-forcing a
six-digit OTP, where an attacker distributed across colocations gets a multiple of the intended
allowance. Treating it as a security control would be a false sense of safety.

### Rejected alternatives

- **Workers `ratelimit` binding alone** — simplest, but inadequate for authentication paths for
  the reason above.
- **Workers KV counters** — KV allows roughly one write per second per key and is eventually
  consistent, which is the wrong shape for a counter.
- **Postgres for everything** — accurate, but puts a write on the hot path of every request and
  spends the database budget on traffic that the edge should have dropped.

### Consequences

Three mechanisms to understand and document rather than one. Durable Objects introduce a
Cloudflare-specific dependency, so it sits behind an interface in `lib/security/` per the
portability rule. Every endpoint in `docs/SECURITY.md` §11 must name which layer protects it.

## ADR-018 — Referral events are pruned and rolled up from day one

**Status:** Accepted
**Date:** 2026-08-31

### Decision

`referral_events` retains raw rows for 30 days. A daily rollup table holds per-product,
per-day aggregates indefinitely. The prune and rollup ship in the same migration that creates
the table.

### Reason

`referral_events` records one row per outbound click and is the fastest-growing table in the
schema. Neon's Free plan provides 0.5 GB of storage per project (verified 2026-08-31), and
every dashboard and "IMPOSTER DETECTED" calculation reads this data. Counting raw events at
render time is both the slowest and the most expensive way to answer a question that only ever
needs a daily granularity.

Retention added later is a migration against a table that is already too large to migrate
comfortably. It has to be there at creation.

### Rejected alternatives

- **Keep raw events indefinitely** — permits arbitrary future analysis, and fills the database.
- **Aggregate only, no raw events** — cheapest, but removes any ability to investigate an abuse
  pattern or correct a miscount.

### Consequences

A scheduled job is required earlier than the roadmap anticipated. `docs/ARCHITECTURE.md` §9
prefers Cloudflare Cron Triggers for this, which is the smallest available mechanism. Analysis
requiring per-click detail is only possible within the 30-day window.

## ADR-019 — Slugs are stable, with a redirect history

**Status:** Accepted
**Date:** 2026-08-31

### Decision

A `product_slug_history` table records every slug a product has ever had. Requests to a
retired slug return a permanent redirect to the current canonical URL. Slugs are never reused
across products.

### Reason

FailProducts depends on accumulated search authority at `/products/[slug]`. Products get
renamed — repositioning is one of the things a struggling product does most often, and
recovering products frequently rebrand. A rename without a redirect discards every inbound
link and every ranking the page had earned, permanently, and the loss is invisible until
traffic is already gone.

Slug reuse is separately dangerous: a new product inheriting a retired slug also inherits
another product's inbound links and any reputation attached to them.

### Rejected alternatives

- **Immutable slugs** — solves it, but forces a product to keep a URL that no longer matches its
  name, which is worse for both users and search.
- **Redirect table keyed only by the latest slug** — breaks on a second rename.

### Consequences

One extra table and a lookup on 404. The reserved-slug list (`new`, `api`, `admin`, `u`,
`status`, `categories`, and similar) must be enforced at creation across all four
slug-shaped namespaces.

## ADR-020 — Images are resized client-side, stored in R2, transformed on read

**Status:** Accepted
**Date:** 2026-08-31

### Decision

The browser resizes and compresses an image before upload. The server validates it by magic
bytes, stores it in R2 under a server-generated key, and serves it through Cloudflare image
transformations. No server-side image processing library is used.

### Reason

`sharp` and every other native image library requires N-API binaries and cannot run on
Workers, so server-side processing is not available regardless of preference. Beyond that, the
August 2026 Next.js critical advisory was an unauthenticated RCE reached through AVIF handling
in the image optimizer — user-supplied images decoded on the server are a demonstrated
high-severity surface, and this design does not decode them on the server at all.

Client-side resizing also cuts upload bandwidth and R2 Class A operations.

### Rejected alternatives

- **Server-side processing in a Worker** — not possible with native libraries; a WASM decoder
  would fit the CPU budget poorly and re-introduce the decode surface.
- **Accept originals unprocessed** — burns R2 storage and serves multi-megabyte images to
  mobile users on a page that must stay fast.

### Consequences

Client-side resizing can be bypassed, so server-side size and magic-byte validation are
mandatory, not advisory. SVG is rejected outright — it is a stored-XSS vector, and rasterising
it would require the decoding step this decision avoids.

## ADR-021 — UUIDv7 primary keys

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Internal primary keys are UUIDv7. Public URLs use slugs and usernames, never raw identifiers.

### Reason

The architecture called for "UUID/ULID-style" identifiers without choosing, and the choice has
index consequences. Random UUIDv4 keys scatter B-tree inserts across the index and fragment it;
UUIDv7 embeds a timestamp prefix so inserts stay roughly sequential, which matters most on
exactly the high-insert tables this schema has — comments and referral events.

UUIDv7 also gives creation-time ordering for free, removing a sort column from cursor
pagination.

### Rejected alternatives

- **Serial integers** — best index behaviour, but leaks row counts and enables enumeration on
  any endpoint that takes an id.
- **UUIDv4** — no ordering, and worse insert locality on the tables that need it most.
- **ULID** — equivalent properties, but not a native Postgres type and needs an extra
  dependency to generate and parse.

### Consequences

`crypto.randomUUID()` produces v4, so v7 generation needs either a small generation function
or a Postgres-side default. Identifiers are opaque to users, which is intended.

## ADR-022 — Agent-assisted development with human-only commit identity

**Status:** Accepted — agent and skill roster superseded by ADR-023
**Date:** 2026-08-31

### Decision

Development uses specialised AI agents and procedural skills, all committed to the repository.
The roster was three agents (`structure-guardian`, `scope-skeptic`, `security-auditor`) and five
skills when this record was written; ADR-023 replaces that roster. Every commit
is authored solely by the maintainer, with no AI attribution of any kind, and no agent may
merge to `main`.

### Reason

Agent definitions committed to the repository are documentation: a contributor can read the
exact standards their PR will be reviewed against, and run the same reviews locally. Keeping
them out of the repository would make the review process opaque and unreproducible.

Attribution is a separate question from authorship of the work. The git history records who is
accountable for the code, and that is a person. Enforcing this through versioned git hooks
rather than instructions means it holds for parallel agents, for other tools, and for sessions
that never read the project instructions.

### Rejected alternatives

- **AI co-author trailers** — honest about tooling, but clutters history with a fact that does
  not identify anyone accountable, and publishes the maintainer's tooling choices permanently.
- **Agent definitions kept private** — hides the review standard from the contributors expected
  to meet it.
- **Instructions without hooks** — relies on every tool reading the instructions, which
  parallel agents and non-Claude tooling will not reliably do.

### Consequences

`.claude/` is public and must never contain credentials or personal data. The hooks are a hard
dependency of the commit path, so a broken hook blocks all commits — they are kept small and
were verified before adoption.

## ADR-023 — Six review agents, ten skills, and a pre-push verification gate

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Formalise the AI development system as six review agents and ten skills, committed in
`.claude/`, plus a deterministic verification gate (`scripts/verify-changes.sh`) that runs on
every push through `.githooks/pre-push` and again in CI.

Agents: `architecture-reviewer`, `security-reviewer`, `performance-reviewer`,
`product-quality-reviewer`, `release-verifier`, `scope-skeptic`.

Skills: `architecture`, `database`, `ui`, `performance`, `security`, `testing`, `adr`,
`dependency-gate`, `pre-push-verify`, `release-check`.

`structure-guardian` is renamed to `architecture-reviewer` and `security-auditor` to
`security-reviewer`. The `feature-slice` skill is absorbed into `architecture`, and
`db-migration` into `database`. This supersedes the roster stated in ADR-022; the commit
identity, no-merge, and no-attribution rules in ADR-022 are unchanged.

A binding rule is added across the system: **nothing verifiable may be assumed.** Facts
checkable in the repository, in primary provider documentation, or by running a command are
verified before being acted on. Anything unverifiable is labelled, and work touching security,
authorization, personal data, retention, licensing, or moderation stops for a human rather than
proceeding on a guess. Every review agent reports an `Unverified` section.

### Reason

The three original agents covered structure, scope, and security. Nothing owned rendering and
query cost, nothing owned whether a change was good *for users*, and nothing owned the final
go/no-go before a deploy. Those gaps were filled by whoever happened to be reviewing, which
means they were filled inconsistently.

The verification gate exists because this repository is public and its history is permanent. A
secret pushed once is compromised even after deletion, and `main` forbids the force-push that
would remove it. The cheapest place to catch that is before the push, and it must be
deterministic — a script, not a judgement.

Building it surfaced a live defect: GNU grep 3.0, as shipped with Git for Windows, aborts when
`-i` and `-F` are combined. The existing `pre-commit` and `commit-msg` hooks used that
combination for their email-leak guard, so on Windows the guard crashed inside a pipeline,
produced no output, and passed every commit. Both hooks now normalise case with `tr` instead.
That bug is the argument for the whole layer: a guard nobody tests is a guard nobody has.

The no-assumption rule was added because the most common and most expensive agent failure
observed on this project was not a wrong answer — it was a plausible one, produced without
checking, in an area where being wrong is costly.

### Rejected alternatives

- **Keep three agents** — leaves performance, product quality, and release verification
  unowned, which is how they get skipped.
- **A root `agents/` directory, as a tool-neutral layout** — Claude Code discovers `.claude/`
  automatically; a root folder would make the definitions documentation that nothing runs.
  `AGENTS.md` at the root gives tool neutrality without that cost.
- **CI-only verification** — correct but slow. Learning about a leaked secret after it is
  published on GitHub is learning too late.
- **Hook-only verification** — a local hook is bypassable with `--no-verify`. Running the same
  script in CI closes that.
- **An orchestration layer that routes and runs agents automatically** — a system to maintain,
  for a routing table that fits in one page and changes rarely.

### Consequences

Ten skills and six agents is close to the ceiling one maintainer can keep coherent; adding more
requires justification through the complexity gate. The routing table in `docs/AI-WORKFLOW.md`
must stay accurate or reviews get run at random.

The gate blocks pushes. A false positive is friction, so its checks are deliberately narrow and
each was tested against both a passing and a failing case before adoption.

`docs/AGENTS.md` is removed; its governance content moves to `docs/AI-DEVELOPMENT.md` and its
rules to `AGENTS.md`, so that no rule has two homes.

Reversal cost is low. The agents and skills are Markdown, and the gate is one script — deleting
either leaves a working repository. What would be expensive is letting the definitions drift out
of sync with the documents they cite, which CI now checks.

## ADR-024 — MCP access is read-first, and never autonomous over production

**Status:** Accepted
**Date:** 2026-08-31

### Decision

Five MCP servers are documented for development use: GitHub, Cloudflare, Neon, shadcn, and
Playwright. Every operation is classified **read** (safe by default), **write** (requires task
intent), or **destructive** (requires explicit human authorization, every time, with no carry
forward from a previous approval).

No agent performs a destructive operation as a routine step. Deleting production data, dropping
or resetting a database, deleting a resource, removing a deployment, rotating a production
secret, and deploying to production are human actions. Agents may read production to diagnose;
they may not change it unattended.

Neon access is read-only by default, and migrations run against a development branch. Playwright
drives local and preview environments, never production with real user data.

MCP is never required for CI, and never required to contribute.

### Reason

MCP is genuinely useful for the one thing reading the repository cannot do: establishing what is
actually configured and what actually happens in a browser. That is the `AGENTS.md` §3
no-assumption rule extended past the filesystem, and it is worth having.

The same connection that verifies a deployment can delete one. The classification exists so that
capability is deliberate rather than incidental. Destructive operations are rare, individually
consequential, and almost never urgent — which makes a human confirmation cheap relative to what
it prevents.

The database is the only part of this system that redeploying cannot roll back, so it gets the
strictest default.

Requiring MCP for CI would mean a contributor needs Cloudflare and Neon accounts to get a green
check on a typo fix. That is not an open-source project.

### Rejected alternatives

- **No MCP at all** — safe, and gives up real verification. Documentation would keep drifting
  from configuration with nothing to catch it.
- **Full write access, trusting instructions** — instructions are not a permission model, and
  this project's own rules say a guarantee that relies on every tool reading the docs is a
  convention, not a guarantee.
- **A custom MCP proxy enforcing permissions** — infrastructure to build, secure, and maintain,
  for a solo project, when scoped tokens already do most of the work.

### Consequences

Some verification requires a human in the loop, which is slower. That is the intended trade.

The permission model lives in `mcp/README.md` and is enforced by token scope and human
attention, not by code — so it is only as good as the token configuration. The checklist in
`mcp/README.md` §5 exists to make that configuration deliberate.

Adding a sixth server is a complexity-gate decision. Reversal is trivial: delete a config file.

## ADR-025 — Three verification levels, with impact-driven check selection

**Status:** Accepted
**Date:** 2026-08-31

Extends ADR-023, which established the review agents and the pre-push gate. That ADR's counts
(six agents, ten skills) are superseded by this one: eight agents and eleven skills.

### Decision

Verification is organised into three levels, each answering a different question:

```
L1 pre-push    Is it safe to leave the machine?      pre-push-verify + .githooks/pre-push
L2 pre-merge   What could it break, was it checked?  pre-merge-verify + verification-orchestrator
L3 pre-deploy  Is the release ready for production?  release-check + release-verifier
```

Which checks run is selected from two computed inputs — a **change classification** and an
**impact radius** (`LOCAL` → `FEATURE` → `CROSS-FEATURE` → `SYSTEM` → `PRODUCTION-CRITICAL`) —
both emitted by `scripts/verify-changes.sh`, along with a list of changed contracts.

Two agents are added: `impact-analyzer` (blast radius, consumers, regression hypotheses) and
`verification-orchestrator` (runs the L2 pipeline, deduplicates findings, issues one decision).

Every check reports one of `PASS`, `WARN`, `FAIL`, `NOT_APPLICABLE`, `NOT_VERIFIED`. Every
pipeline run ends in exactly one of `PASS`, `PASS_WITH_WARNINGS`, `BLOCK`.

Rules: [`AI-VERIFICATION.md`](./AI-VERIFICATION.md). Lifecycle and worked examples:
[`AI-VERIFICATION-FLOW.md`](./AI-VERIFICATION-FLOW.md).

### Reason

ADR-023 gave the project a gate that answers *is this safe to push* — secrets, identity, branch,
migrations. It does not answer *what could this break*. Those are different questions with
different failure modes: a push leaks a credential, a merge breaks a caller in a file the diff
never mentions.

Selection had no deterministic input. The routing table keys off change class, which a human or
an agent judged by reading paths. Computing a radius from the diff makes the routing decision
reproducible, and makes escalation automatic where it matters — a two-line change in
`src/lib/auth/` is `PRODUCTION-CRITICAL` no matter how small it looks.

The `NOT_VERIFIED` state exists because the repository is pre-implementation and will be
partially unverifiable for a long time. Without a distinct state, a check that could not run gets
reported as passing, and the pipeline starts producing false confidence — the one outcome that
makes verification worse than none. This is `AGENTS.md` §3 applied to the verification system's
own output.

### Rejected alternatives

- **Extend `pre-push-verify` to cover merge and deploy** — one skill, no new concepts. Rejected:
  the pre-push hook must stay fast or it gets bypassed with `--no-verify`, and impact analysis
  plus reviewer orchestration is not fast. Conflating the levels would have made the cheap check
  expensive and the expensive check optional.
- **A single `verification` agent doing analysis, review, and decision** — fewer moving parts.
  Rejected: it collapses "what does this reach" and "is this good" into one pass, and a
  generalist doing both is worse at each than the specialists already in the repository.
- **Root `agents/` and `skills/` directories**, as the original specification described.
  Rejected: Claude Code discovers definitions in `.claude/`, so a root copy would be inert
  documentation and a second, conflicting instruction system — the outcome
  `AI-DEVELOPMENT.md` §8 exists to prevent.
- **Run every reviewer on every change** — simple, no selection logic to get wrong. Rejected: a
  report that is always long is a report nobody reads, and a solo maintainer skimming eight
  reviews catches less than one reading two.
- **A custom orchestration service** — a job runner, a findings database, a dashboard. Rejected
  at the complexity gate: the orchestration is repository instructions plus existing CI, and a
  Stage 0 project does not operate infrastructure to review itself.

### Consequences

Eight agents and eleven skills is the ceiling. Adding another requires removing one, or a
justification through the complexity gate.

The radius heuristic is path-based and deliberately biased towards over-classifying. It will
occasionally route a reviewer at a change that did not need one; the opposite error is more
expensive.

Consumer detection is textual `grep`, not a resolved import graph, so it misses dynamic imports
and re-exports and produces false positives on common identifiers. Documented as a known
limitation rather than hidden.

Most of L2 reports `NOT_APPLICABLE — pre-implementation` until `src/` exists. That is honest and
intended: the pipeline is built before the code so the first feature is verified the same way as
the hundredth.

## ADR-026 — Categories are a fixed, curated taxonomy; tags carry the open vocabulary

**Status:** Accepted
**Date:** 2026-09-01

Resolves open question 5, which blocked Phase 2 slice 2.3.

### Decision

`categories` holds a fixed list, seeded by migration `0006_seed_categories.sql` and specified
in `src/domain/product/category.ts`. Only a migration adds a category; no user-facing path
creates one. A product picks at most one from the list, and the choice is validated
server-side against that list, not against the table.

Thirteen categories ship: AI, Developer tools, SaaS, Productivity, Marketplace, Social,
E-commerce, Fintech, Health, Education, Games, Hardware, and Other.

`product_tags` is unchanged and remains the free-form axis. The `tags` table shape already
allows user-created rows; nothing in this decision closes that door.

The domain module is the source of truth, including the row ids, which are literal UUIDv7
values. The migration writes exactly those rows.
`tests/integration/category-taxonomy.test.ts` fails if the two ever disagree.

### Reason

`docs/PRODUCT.md` §10 already drew this line without naming it: a Category is a "normalized
classification" and a ProductTag is a "flexible discovery label". Those are two different
jobs, and the schema already has two tables for them. The open question was really whether to
collapse them, and collapsing them loses the navigable axis.

`docs/PRODUCT.md` §9 is the constraint that settles it: "Only index useful, unique pages. Do
not generate thousands of thin parameterized pages." A free-form taxonomy generates exactly
that, and it does so from typos and casing alone — `ai`, `AI`, `A.I.`, and `artificial
intelligence` become four indexable pages holding one product each. Nothing in a Stage 0
budget cleans that up.

`docs/ROADMAP.md` Phase 4.5 requires "at least one worked example per category, so no category
page is empty on arrival". That target is only meaningful against a finite list; against a
free-form one it cannot be stated, let alone met.

Ids are literal rather than `gen_random_uuid()` so every environment holds the same id for the
same category. A fixture, a dump, and a fresh branch then agree, re-running the seed is a
no-op, and the domain module can hand an id straight to a query filter. `gen_random_uuid()`
would also produce v4 keys, against ADR-021.

### Rejected alternatives

- **Free-form, created on submit** — maximum flexibility, and it hands an anonymous-ish input
  the power to create indexable pages. It contradicts `PRODUCT.md` §9 directly, and it makes
  every category page's emptiness a permanent possibility.
- **Fixed list plus a moderator UI to extend it** — the same schema as this decision, with
  dashboard surface that belongs to Phase 3 moderation. Deferred, not rejected: adding it later
  changes no column.
- **No categories at all, tags only** — simpler, and gives up the one navigation axis that
  answers "who else tried this?", which `docs/PRODUCT.md` §2.3 treats as the product's core
  value.
- **Seeding from the domain module at application start** — removes the duplicate list, and
  makes the database's contents depend on deploy order rather than on a migration. Schema and
  seed belong in the same audited, ordered place.

### Consequences

Adding a category is a migration and a PR, not a form field. That is the intended friction: a
taxonomy that anyone can extend at any time is not a taxonomy.

"Other" exists and will accumulate. A junk drawer is a real cost and still the cheaper one —
without it a founder has to file their product under something it is not, and deliberate
mislabels are less recoverable than an honest overflow bucket. If Other grows past a useful
share of the directory, that is the measurement that justifies splitting it.

Two copies of the list exist, in the domain module and in the migration. The integration test
is what makes that safe; without it the pair would drift and `/categories/[slug]` would 404 for
reasons nothing in the code explains.

Category slugs join usernames, product slugs, and tag slugs in the reserved-name namespace
(ADR-019). A unit test asserts no curated slug is reserved.
